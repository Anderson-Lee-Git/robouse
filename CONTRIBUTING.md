# Contributing to Robo Use

Thank you for helping. Bug reports, task fixes, new tasks and suites, harnesses and documentation are all welcome. Everyone taking part follows the [Code of Conduct](CODE_OF_CONDUCT.md). Security problems go to [SECURITY.md](SECURITY.md), not to a public issue.

## Before you start

- For a bug, open an issue with the steps that show it, unless it is a one-line fix.
- For a new suite, harness or a change to the task format, open an issue first and describe the design. These touch the task format, the episode server or the scoring, and are easier to agree on before the code exists.
- Questions and early ideas are welcome on the BenchFlow [Discord](https://discord.gg/mZ9Rc8q8W3).

## Development setup

You need Python 3.12 (the package supports 3.11 to 3.13; the type checker and the maintainer tools need 3.12) and [uv](https://docs.astral.sh/uv/). On Linux without a display, install OSMesa (`sudo apt-get install -y libosmesa6`) so MuJoCo can render offscreen.

```sh
git clone https://github.com/benchflow-ai/robouse.git && cd robouse
uv venv --python 3.12
uv pip install -e ".[sim]" --group dev
.venv/bin/robouse doctor
```

The `dev` group (in `pyproject.toml`) holds pytest, ruff, mypy and their pins. Add the extra of any simulator you work on, for example `".[sim,metaworld,gymrobotics]"`. Suites whose simulator needs its own virtualenv (dexjoco, driving, dmcontrol, myosuite, humanoidbench, maniskill, robocasa) say how to set it up on their page under `docs/suites/`.

## Checks

Run these before you open a pull request. They are the checks the CI workflow (`.github/workflows/ci.yml`) runs on every pull request, which also scans the history for secrets with gitleaks (`.gitleaks.toml`). `pre-commit install` runs ruff and gitleaks on every commit (`.pre-commit-config.yaml`).

```sh
uvx ruff@0.14.3 check .
uvx ruff@0.14.3 format --check .
.venv/bin/pytest -q
```

Type checks (`mypy` reads its file list from `pyproject.toml`):

```sh
.venv/bin/mypy
```

No check needs a model API key, and tests must not make model API calls. Use the fakes in `tests/fakes.py` instead.

Some tests skip, with a reason, when what they need is missing: a simulator's own virtualenv, MuJoCo Menagerie models (`robouse fetch-assets`), or an MCP SDK checkout. Two markers name the rest. `needs_benchflow_embodied` tests need BenchFlow's embodied layer and task-format hook, which no BenchFlow release has yet, so they skip everywhere outside the maintainers' setup. `maintainer` tests cover the maintainers' tools under `tools/`, which need Python 3.12; they skip on 3.11. `pytest -m "not maintainer"` leaves them out.

## Changing or adding a task

A task is ready when its reference solution scores 1 and its no-op control scores 0:

```sh
.venv/bin/robouse tasks check tasks/<suite>/<task>
```

[Write or compose a task](https://robouse.ai/docs/write-a-task/) and the [task.md reference](https://robouse.ai/docs/task-format/) describe the format. In addition:

- Do not put anything in the agent's view that gives away the answer: hidden object positions in `robo observe` or `robo info` output on a vision task, goal positions on a fixed grid, or a start pose that touches the target. If a task gives the agent camera parameters or fixture positions on purpose, say so in the instruction.
- Adapted tasks keep the source benchmark's success rule where it has one. Say in the suite's page what you changed and why.
- Most suites are generated by a script under `adapters/<suite>/`. Change the generator and regenerate the folders rather than editing generated task folders by hand.

## Changing the sandbox, the episode server or scoring

These decide whether a score means anything. A pull request that touches `src/robouse/runner/sandbox.py`, `src/robouse/core/`, a backend's judge or the harness launchers should say what an agent can and cannot do afterwards, and include a test (see `tests/test_cheating_agent.py` and `tests/test_session.py`). If it changes what the sandbox allows, update [SECURITY.md](SECURITY.md) in the same pull request.

## Documentation

- The public docs (the pages listed in `PAGES` in `tools/docs/build_docs.py`, published at [robouse.ai/docs](https://robouse.ai/docs/)) describe only what is implemented and tested. Run every command you add to a public page, as written, on a clean install, and paste its real output.
- `docs/cli.md` and `docs/configuration.md` are generated by `tools/docs/cli_reference.py` and `env_reference.py`, and the tables in `docs/suites.md` (between the `<!-- suites-table -->` and `<!-- hub-only-table -->` markers) by `suites_reference.py`. Change the code or the generator, not the generated text.
- Write one line per paragraph and one line per list item in Markdown; do not hard-wrap prose.

## Vendored code

`src/robouse/backends/capx/capx_upstream/` (with PyRoKi's snippets inside it) and `src/robouse/backends/rlebench/rlebench_upstream/` are copies of CaP-X and RLE-Bench under the MIT License. Keep changes there to a minimum, and record each change in the `VENDORED.md` beside the code.

New third-party code, data or assets need a license that allows redistribution and commercial use (no non-commercial or no-derivatives terms), the license text next to the files or in `licenses/` (and in `license-files` in `pyproject.toml` if the package ships them), and an entry in `NOTICE` with the source, commit, license, copyright line and paths. Record the source in data files themselves too, as `src/robouse/real/data/so101_chain.json` does. Do not commit renders of assets whose license forbids redistribution, such as the BEHAVIOR Data Bundle.

## Maintainer-only parts

Some of the repository serves the maintainers' own runs and infrastructure, and contributors can ignore it: `tools/ops/`, `tools/gpu/`, `tools/site/` and `tools/analysis/` (see `tools/README.md`), `docs/benchflow.md`, `docs/viewer.md` and the other pages the docs site does not publish (`EXCLUDED` in `tools/docs/build_docs.py`), and the optional credential pools in `src/robouse/_maintainer.py` (`ROBOUSE_CLAUDE_TOKEN_FILE`, `ROBOUSE_CODEX_AUTH_DIR`). Machine-specific settings for them come from the environment, never from the repository.

## Pull requests

- Branch from `main` and open the pull request against `main`. Keep it to one change; split unrelated fixes.
- Write commit messages that say what changed and why, in plain sentences.
- To bring your branch up to date, merge `main` into it; there is no need to rebase.
- Do not commit credentials, `.env` files, run folders (`runs/`) or large binary files. Robot models and benchmark assets are downloaded at run time (`robouse fetch-assets`), not committed.
- A maintainer reviews every pull request. Changes to scoring, the sandbox or the task format need a maintainer's approval before merge.

## Releases

A release is a pull request and a tag.

1. In the pull request, bump the version in `src/robouse/__init__.py`, `docs/suites.md`, `docs/supported.md` and the supported page's description in `tools/docs/build_docs.py`. Regenerate `docs/cli.md` with `tools/docs/cli_reference.py` against the built wheel, and turn the changelog's top section into `## X.Y.Z (YYYY-MM-DD)`, dated the day it goes to PyPI (UTC).
2. Merge it, tag the merge commit and push the tag: `git tag -a vX.Y.Z -m "robouse X.Y.Z" <commit> && git push origin vX.Y.Z`.
3. `.github/workflows/release.yml` checks that the tag, the package and the changelog agree. It builds the package, installs the wheel and publishes to PyPI through trusted publishing, so no token is stored. PyPI's trusted publisher for `robouse` is: owner `benchflow-ai`, repository `robouse`, workflow `release.yml`, environment `pypi`.
4. Rebuild robouse.ai/docs from the tagged commit (`tools/docs/build_docs.py --out <site checkout>/site/docs`) and deploy the site.
